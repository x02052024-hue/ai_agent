# ai_agent

Интерактивный чат-агент (`agent.py`) через OpenAI-совместимый API с TOOL
`run_shell` (полноценный shell), логами API/инструментов и сохранением истории.
Конфигурация — `../config.yaml` (пример в начале `agent.py`).
Модульные тесты — `test_agent.py` (`python -m pytest test_agent.py -p no:libtmux`).

## Стандарт проектирования, разработки и программирования (для реализации LLM)

Настоящий раздел описывает стандарт, характерный для данной программы —
интерактивного чат-агента, построенного поверх LLM через OpenAI-совместимый API
с поддержкой TOOL (function calling).

### 1. Архитектура и проектирование

* **Единая точка входа.** Программа реализована одним модулем `agent.py` без
  внешних фреймворков: минимум абстракций, максимум прозрачности потока данных
  (конфигурация → цикл чата → вызов API → обработка tool_calls → логирование).
* **Клиент-серверная схема с LLM.** Взаимодействие с моделью ведётся строго
  через стандартизированный протокол `chat.completions` (OpenAI-совместимый
  `base_url`), что обеспечивает переносимость между облачными и локальными
  инференс-серверами (vLLM, llama.cpp server, Ollama и т. п.) без изменения кода.
* **Паттерн «агент + инструменты» (ReAct/tool-use).** Модель описывает намерение
  выполнить действие через структурированный вызов функции `run_shell`
  (JSON-схема параметров); исполнение стороны клиента, результат возвращается
  модели в роли `tool`. Цикл повторяется до получения финального текстового
  ответа — детерминированная машина состояний вместо свободной генерации.
* **Разделение конфигурации и кода.** Ключ API, URL и имя модели вынесены во
  внешний файл `../config.yaml`; секреты не хранятся в исходном коде. Пример
  конфигурации (`EXAMPLE_CONFIG`) включён в модуль и используется как источник
  истины для сообщений об ошибках и тестов.
* **Надёжность ввода-вывода.** Все файловые операции выполняются в кодировке
  UTF-8; ошибки конфигурации поднимаются как типизированное исключение
  `ConfigError` и обрабатываются в `main()` с корректным завершением (`sys.exit(1)`).

### 2. Специфика реализации для LLM

* **Системный промпт как контракт качества.** Системное сообщение явно задаёт:
  язык ответов (русский), запрет нечитаемых символов при кодировке UTF-8
  («кракозябр») и способ вызова инструмента. Требования системного промпта
  проверяются модульными тестами, а не только эвристиками.
* **Function calling / TOOL.** Описание инструмента передаётся модели в начале
  каждой API-сессии в формате JSON-схемы (`type: function`, `parameters`,
  `required`); `tool_choice="auto"` оставляет выбор стратегии модели. Неизвестные
  имена инструментов не приводят к падению — возвращаются модели как ошибка в
  сообщении роли `tool`.
* **Управление контекстом.** Полная история диалога (system/user/assistant/tool)
  сохраняется в `chat_history.jsonl` (по одному JSON-объекту на сообщение,
  `ensure_ascii=False`) и может быть очищена командой `clear` с сохранением
  только системного промпта.
* **Толерантность к генерации модели.** Аргументы tool-вызовов парсятся из JSON
  защищённо (`json.JSONDecodeError` → пустые аргументы), значения по умолчанию
  (`timeout=60`) и приведение типов выполнены до исполнения команды; пустой
  ответ модели (`content=None`) не является ошибкой.
* **Наблюдаемость LLM-взаимодействий.** Каждый запрос/ответ фиксируется в
  `api.log` (тексты пользователя и модели ограничиваются 20 символами —
  компромисс между приватностью и трассируемостью), каждый вызов инструмента —
  в `tool_usage.log` с полными аргументами, кодом возврата и превью результата
  (200 символов). Это даёт воспроизводимый аудит поведения модели.
* **Безопасность исполнения.** Shell-команды выполняются с таймаутом
  (`subprocess.run(..., timeout=...)`), вывод (`stdout`/`stderr`/`returncode`)
  возвращается модели в структурированном JSON; исключения исполняющей среды
  преобразуются в сообщения об ошибках для модели, а не в аварийное завершение.

### 3. Стандарт программирования

* Python 3, стиль по PEP 8: модуль с shebang и coding-директивой, докстринги
  на русском языке у каждого значимого объекта, констаны верхнего регистра
  (`SYSTEM_PROMPT`, `RUN_SHELL_TOOL`, пути файлов), магические числа вынесены
  в параметры функций со значениями по умолчанию (`truncate(text, limit=20)`).
* Только проверенные зависимости с диапазонами версий в `requirements.txt`
  (`openai>=1.30,<2.0`, `PyYAML>=6.0,<7.0`); зависимости для тестирования —
  отдельно, в `requirements-dev.txt`.
* Точка входа отделена от логики: `if __name__ == "__main__": main()`, функции
  чистые и тестируемые в изоляции (пути файлов — модульные переменные,
  переназначаемые через `monkeypatch`).

### 4. Тестирование и качество

* Модульные и интеграционные тесты в `test_agent.py` (pytest): проверка
  ограничения логов, загрузки конфигурации и обработки ошибок, формата записей
  `api.log`/`tool_usage.log`, сохранения истории, выполнения shell (включая
  таймаут), соответствия системного промпта и JSON-схемы TOOL, а также цикла
  чата `main()` с мок-API и `tool_calls`.
* Автофикстура `redirect_logs` изолирует все побочные файлы во временную
  директорию (`tmp_path`) — тесты не оставляют артефактов и воспроизводимы.
* Запуск: `pip install -r requirements-dev.txt && python -m pytest test_agent.py -v`.

### 5. Эксплуатация

* Установка: `pip install -r requirements.txt`.
* Настройка: создать `../config.yaml` по примеру `EXAMPLE_CONFIG`
  (`api_key`, `base_url`, опционально `model`).
* Запуск: `python agent.py`; выход — `exit`/`quit`/`выход`, очистка истории — `clear`.
* Артефакты сессии в каталоге программы: `api.log`, `tool_usage.log`,
  `chat_history.jsonl`.
